The split, mapped

What each top-level part of the repository would do once the asset split and the #134 separation are both built, which parts may rely on which, and where the code would still repeat itself. Written for deciding whether the cut is in the right place.

Updated 2026-11-03 with your four decisions; corrected 2026-11-02 evening. The first version said domain/ (now renamed asset_model/) held the agencies, collections and schedule. It does not: each asset defines those itself, and asset_model/ is only the code that reads them. Its line counts were mostly docstrings, and it described several proposals as if they were already true. A fact-check against the code found 16 more errors, all fixed below. Anything marked proposal is what #134 would build, not how the code works today.

Sources: the moved tree (wip/bmove), the draft docs/drafts/separation-v3.yaml, an import scan of the moved tree, and running-thoughts #137's simplification review. "Code lines" leave out docstrings, comments and blank lines.

Definitions live in each asset; shared code reads them

Two different kinds of thing keep getting mixed up, so they are separated here first.

Per asset: the definitions

  • Agencies, collections and datasets: assets/<asset>/data-asset.yaml, under hierarchy:.
  • The delivery schedule: assets/<asset>/calendar.yaml. It holds the named calendars, their authored dates and versions, which calendar each dataset is on, and what each dataset owes when.
  • The time zone, versioned: data-asset.yaml, under timezone:.
  • Checks, contracts, people, presentation, and the asset's own dbt project.

Shared: the code that reads them

  • hierarchy.py answers "what datasets are in this collection?" and "which dataset owns this table?".
  • schedule.py and slots.py answer "which period is due when?" and "when does this slot open and close?".
  • asset_time.py applies the asset's time zone and answers "what time is it now on this asset?". Every recorded timestamp goes through it.
  • None of these hold an agency, a collection or a date of their own. They are shared so that the pipeline and the generator read the same files the same way.

Each asset has its own dates, but they all use one calendar mechanism: named calendars of authored dates, with each dataset picking one. Whether an asset may ever need a different kind of calendar, rather than just different dates, is an open question. See decision 1.

How DRY it will be

Mostly fine where it matters. Things held once, or held equal on purpose:

  • dbt macros and generic tests, in dbt_shared/.
  • Warn and fail thresholds for targeted fault injection, read from each tool's own files. Not yet for generator/dirty.py, which still copies Soda and dbt thresholds as constants (risk 3).
  • Status words in Python and on the page, held equal by shared test cases that neither side owns. The copy is justified: the page has no build step, and ticketing runs without a browser.
  • File checks: defined once per asset, with ids derived per dataset. The two assets' copies are identical (risk 2).

Between the two assets, most of the repetition is deliberate. Their contracts, checks, adapters and providers share anywhere from a few percent to about half their lines, depending on the pair, and mostly as structure, because they describe different collections for different teams.

The real risks, most important first:

  1. The same rule written several times in the schedule code

    Found by the simplification review (#137). The step that maps a round to the period its files fill is written in six places, one of them in the Child Protection provider with no bounds check. Which participation version gives a slot its inputs is resolved three times per slot. "Does this dataset supply in round R" is written three ways, and one is narrower than the others, so they might disagree (not yet confirmed). Three modules each read synthetic: true for themselves.

    Decided: one helper per rule, in asset_model/. Gone to the scoper with #134 (#137 groups B-D).

  2. Allowed values in up to five places per collection

    Civil Registration's valid suburbs sit in five places: the contract, the Soda checks, the dbt schema, the QA adapter and generator/names_au.py. No test holds them equal.

    Decided (D3): the contract, Soda and dbt copies stay while the tool comparison runs (one or more will go). The QA adapter reads the list from the contract at run time, so its hand copy goes. The generator's pools stay independent: test data need not follow the rule exactly.

  3. Files identical, or nearly, in both assets

    Byte-identical: file-checks.yaml (118 lines), the dbt project file, packages.yml, the dbt package lock and the 35-line forwarding macro. Nearly identical: people.yaml (120 of about 126 lines shared) and data-asset.yaml (266 lines shared, 84% of the daily one). These will drift apart one asset at a time.

    Decided (D2), file by file: file-checks.yaml becomes one shared default an asset can add to or override; the dbt package files stay per project (dbt needs them) but must be identical, with a gate that fails if they differ; people.yaml and data-asset.yaml stay copied with no gate, since each team owns its own. The forwarding macro is gone and the dbt projects are renamed mothman_<asset> (C12, C13, built).

  4. Near-copies the function move misses

    Besides the main status order in dataset_status.py, the order is copied three more times: once more in the pipeline (rechecking.py), once in the bootstrap (target_agreement.py) and once in a provider (linkage_products.py). The Child Protection provider restates the quarterly calendar's quarters. generator/dirty.py hard-codes fault rates sized to Soda and dbt thresholds written in comments. The geocoding verdict table (GEO_FAULT_VERDICT) is hand-written.

    Decided (D4): all of these join #134 - the status order moves into asset_model/, the Child Protection provider reads the quarterly calendar, dirty.py reads thresholds through the reader Linkage Products uses, and the verdict table is derived.

  5. Geocoding checks, about 330 hand-copied lines per new source

    Each geocoded dataset's Soda, dbt and contract files are near-copies: the two sources' Soda files share 75% of their lines and their dbt schemas 94%. Deliberate for now. On 28 October you agreed the Linkage Keys check files would be hand-written for now, and the geocoding checks were built the same way.

    Would fold it: only worth doing if many more sources are coming. The file checks' "derive per dataset" pattern is the template.

  6. Status copies inside the page itself

    Three places in the dashboard template repeat its own status order or words. One of them deliberately words two statuses differently: the cross-table view says "No result" where the rest of the page says "No data" and "No rule defined".

    Would fold it: point two of them at the page's one copy. The third needs a decision on its wording first.

What the cut has to get past

  • Moving the shared functions is not cheap. Some of the pure functions the generator calls sit inside large pipeline modules (promotion.py is 1,388 lines) and import the database layer, so they have to be pulled out rather than moved. REQ-PIPE-380's "report to Keith if a function can't move" will probably fire.
  • The providers break the rule as it's worded. REQ-GEN-386 lets providers import only asset_model/, scenarios/ and outside libraries, but today they import generator/ 65 times and the population generator once.
  • About half of the four modules' text is docstrings, much of it history already recorded in requirements.yaml. The safe tidying (#137 group A) comes before the move and makes it smaller.

What you decided (2026-11-03)

  1. The cut is right, and the shared package is called asset_model/ rather than domain/. Every asset keeps one calendar mechanism with its own dates; a project extraction with no cadence is a calendar with no slots.
  2. Identical configuration, file by file: shared file-checks.yaml; dbt packages identical by gate; people and data-asset files stay per asset.
  3. Allowed values: three tool copies stay for the comparison; the adapter reads the contract; the generator stays independent.
  4. Near-copies join #134.
