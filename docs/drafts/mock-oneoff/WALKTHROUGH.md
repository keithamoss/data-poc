## 1. The mock's story

**Project RX-0417, "Readmission after an emergency department visit, 2021-2024"** is a fictional study at a fictional "Example University". The researchers asked for every ED presentation at five study hospitals in 2021-2024, the inpatient admissions of those people in the same window, and any death registration for them up to 30 June 2025. Two (mock) agencies supply it:

| Agency | Collection | Dataset (table) | Rows | Notes |
|---|---|---|---|---|
| Hospital Services Agency (mock) | Emergency Care | ED presentations (`ed_presentations`) | 240 | identifier `presentation_id`; cohort on `presentation_date` |
| Hospital Services Agency (mock) | Inpatient Care | Hospital admissions (`hospital_admissions`) | 96 | identifier `admission_id`; cohort on `admission_date` |
| Hospital Services Agency (mock) | Inpatient Care | Quarterly readmission summary (`readmission_summary`) | 16 | **derived product**; identifiers `year` + `quarter` |
| Civil Registry Office (mock) | Death Registrations | Death registrations (`death_registrations`) | 11 | identifier `death_registration_id`; cohort on `date_of_death` |

The data were generated by a small seeded script (`scripts/make_package.py`). Four realistic problems were planted:

1. **A null identifier**: one ED presentation has an empty `presentation_id`.
2. **A value outside the cohort**: one admission is dated 2025-02-14 (the cohort ends 2024-12-31).
3. **A wrongly typed value**: the derived summary has `readmission_rate = "suppressed"` in a `number` column (a suppressed cell written as text).
4. **An undeclared extra file**: `linkage_keys_DRAFT.csv`, the analyst's draft linkage keys, sent by mistake.

Everything else is clean, so the page shows a realistic mix: one agency failing, one passing.

The recipe (format v1, the stand-in until the real downstream format arrives via a translator) and the first lines of each CSV are in **Appendix B**.

| File | What it is for |
|---|---|
| `data-asset.yaml` | The one-off's identity and hierarchy, built from the recipe: `data_asset_id`, project, the recipe's format version, sha256 digest and filter text; a timezone (the deployment's, Australia/Perth); the agencies/collections/datasets with generated shorts (`a1`, `c1`...), each dataset's arrival pattern (its file name), declared columns with types and primary-identifier marks, cohort bounds and expected row count (criterion 2). |
| `calendar.yaml` | Minimal: every dataset `no_calendar: never` (a one-off owes no schedule), `derived: true` on the summary (REQ-PIPE-438). |
| `presentation.yaml` | The page's words, in the recipe's own names (agency blurbs, delivery format "CSV (extraction package)", provenance). |
| `<agency>/<collection>-contract.yaml` | The datacontract-cli ODCS contract per collection: schema from the recipe's columns, plus the RECIPE LAYER checks as contract quality rules (declared type, cohort bounds, expected rows - REQ-QAC-441 c4-5). |
| `<agency>/<collection>-soda-checks.yml` | The same recipe-layer checks as Soda checks. |
| `<agency>/<collection>-evidently-checks.yml` | Evidently's share (expected rows). |
| `*-retired.*` siblings | Empty retired-check files, the same shape every enduring collection has (REQ-QAC-241), so the shared tools find them. |
| `dbt/dbt_project.yml`, `dbt/packages.yml`, `dbt/models/<collection>/{sources,schema}.yml`, `stg_*.sql` | A dbt project per one-off: staging views over the loaded tables, the recipe-layer checks as dbt tests, `dbt_shared` reached by relative path, and dbt_utils read from `MOTHMAN_ONE_OFF_DBT_UTILS` so no machine path is committed (criterion 12). |
| `generated.sha256.json` | The recipe digest and a digest of every generated file (criterion 5); the load refuses if the recipe beside the package no longer matches (criterion 8). |

**What is deliberately NOT there** (REQ-PIPE-440 criterion 13, Keith 2026-11-21): no `people.yaml`, no default check layer, no publishing destination, no QA adapter, no `synthetic/`. Those live once, in the kind's template, and are read live at the step that needs them:

- `one-offs/extraction/_template/default-checks.yaml` - the DEFAULT LAYER every extraction is held to (`table_arrived`, `undeclared_file`, `columns_arrived`, `identifier_not_null`), read at each load.
- `one-offs/extraction/_template/people.yaml` - who may record a release decision (Keith, qa+manager; Brian Cohen, placeholder), read at `decide`.
- `one-offs/extraction/_template/publishing.yaml` - where pages go (`data/one-off-pages`, gitignored, settled by Keith for the PoC), read at `publish`.

Why not copied: a change to any of them reaches every extraction loaded/decided/published after it, and the commit the page names says which version applied. The template must itself be committed and pushed before a load reads it (the same git refusal applies to it). The three template files are reproduced in full in Appendix D.

## 4. Findings

### Defects

**D1. An undeclared file makes its home dataset Fail, but nothing above or on that dataset agrees.** (Likely in the dashboard template; the package check's history point has `attempt: null` and empty `receivedAt`/`run_date`.)

Reproduction (done, `repro-undeclared-only`): the same package with the three data problems fixed, so the undeclared `linkage_keys_DRAFT.csv` is the only problem. Open, commit, push, load, publish.
- `load` prints `81 tool result(s), 0 failing; not declared, not filed: linkage_keys_DRAFT.csv`.
- The page's home says "Fail - A file the recipe does not declare arrived ... it fails the ED presentations dataset's 'Only declared files' check, which counts in that dataset's QA result", and its tier legend counts Pass (2), Fail (0).
- The Hospital Services agency card and the Emergency Care collection both show **Pass** while their own subtitle says "1 of 1 dataset not passing, 1 failing" (`R2-repro-agency.png`). That is a false green one level up.
- The ED presentations dataset shows **Fail**, but every column is "All 5 passing" and its file section says "All 7 file checks passed ... never change the status" (`R3-repro-ed-dataset.png`). No failing check is named anywhere on the dataset page.
- Cause of the last point, read from the template: `fileAttemptInPlaceOn()` keeps only history points whose `attempt` equals the newest file attempt, and the undeclared-file point has `attempt: null`, so it is filtered out. Even if it were shown, that section's wording ("This file was refused ... none of its data was loaded") would be wrong for a package check.
- The existing end-to-end test only asserts the home-view mention (`test_the_undeclared_file_is_named_once`), and its fixture also has data failures on the home dataset, which hides all of this.

**D2. Default-layer checks lose their names and prose on the page.** The template's `default-checks.yaml` gives every default check a name, description and "what a failure means", and the load renders those into the tools' files (`data/<id>/qa/config/...`, e.g. dbt `meta: name: Identifier recorded, description: This value must never be empty.`). On the published page they show as the tools' raw names - `dbt:not_null`, `missing_count(presentation_id) = 0`, `Schema Check` - with no "What this check does" or "What a failure means" (`10-check-identifier-recorded-dbt.png`; the embedded data has no `description`/`failure_indicates` for them). Recipe-layer checks are fine ("Inside the cohort" with both texts, `08-...png`). Likely cause: `pipeline/build_dashboard_data.py` looks up check prose with `collect_checks(None)` over the committed folder, which does not contain the default layer (by design it is never copied in). Not reproduced with a separate test; evidence is the page and its embedded JSON.

**D3. `one-off list` recommends a step that will be refused.** After the repro was published and dropped, `list` shows `repro-undeclared-only ... pushed ... next: mothman one-off load --id repro-undeclared-only <package>`, and that load is refused: "page is already published ... it is not loaded again" (`captures/r5-load-after-drop.txt`). The list's stages (opened/committed/pushed/loaded) have no "decided" or "published", so after publishing the main mock it still says `loaded`, next "publish".

**D4. `one-off list` labels enduring-asset databases as one-off databases.** `supply_daily_c` and `supply_quarterly_c` (141 runs, no `qa.one_off_load` table - an enduring asset's database, from another session using a suffixed DSN) are listed under "One-off databases on the server". `stray_databases()` treats every `supply_*` that is not exactly `supply_<enduring asset>` as a one-off. Minor, but a person could try to drop the wrong thing on that advice.

### Rough edges and confusing wording

- **F1. Load output noise.** Each collection repeats "note: delivery '...' carries ..., which nothing is currently owed from - processed as usual" for every earlier delivery too (fifteen such lines for three deliveries). For a one-off nothing is ever owed, so the note says nothing useful.
- **F2. Gate line in shouting caps.** "arrival pattern validation OK - 4 dataset pattern(s), NO DATABASE REACHABLE, so duplicate attribution was not checked" - the gates run before the one-off's database is created, so this is always printed. "schedule validation OK - 0 calendar(s)" sits beside a generated `calendar.yaml`.
- **F3. Counts that do not match each other.** `load` says "81 tool result(s), 10 failing"; the database holds 112 check results, 11 failing (the package checks are not in the 81); publish says "17 ... (4 fail)", "50 ... (6 fail)", "14 ... (0 fail)". Each is defensible, but three different totals for one load is confusing.
- **F4.** See D4.
- **F5. Publish output noise.** Four "note: could not read closed periods ... NoCalendarAgreed ... (no_calendar: never)" lines, plus "PERIOD_SEQUENCES = , ending at", "ASSET_TIMEZONES = Australia/Perth from 1970-01-01", empty CHANGELOG/RELEASE_NOTES/TICKET/LEADERBOARD/FEEDBACK lines, and "GITHUB_LINKS = 81 check link(s)".
- **F6. The derived product fails but is not counted.** The decide summary lists "Quarterly readmission summary: Fail", the page shows it Fail "Derived product, not counted in the extraction's status", and nothing rolls up. That is the design (REQ-PIPE-438), but a reader of the home view sees no sign that a third dataset is failing.
- **F7. Enduring-asset wording on a one-off page.** "Awaiting a decision - ... not in place in the warehouse yet. Nothing is in place in the warehouse for this period yet."; "Latest arrival: Unknown ... waiting 2m" (the receipt's `originally_received: not-known`); "Real-time QA state ... for internal data teams and this agency's own data providers"; "Rolled-up status across every agency in the multi-agency data asset"; the footer's "including cross-table foreign-key and business-rule checks where a collection has more than one table" (recipe v1 declares none); Inpatient Care shows a "Cross-table checks - No automated quality rule defined" box; the page still carries a Feedback link, Time travel and Cadence-aware viewing panels, and a Leaderboard drawer.
- **F8. A null sole identifier cannot be named.** The identifier check's example key is "(no value)" (`10-...png`): failing rows are recorded only by their identifiers, so a row whose only identifier is empty cannot be found from the page. Probably inherent; worth a sentence on the page.
- **F9. "View on GitHub" links on a one-off page.** They point at `github.com/keithamoss/data-poc/tree/<commit>/one-offs/extraction/...`. A one-off "never uses GitHub" (REQ-PIPE-446 c14), and the link only works if the one-off's commit was pushed to that repository.
- **F10. Names shown twice.** The agency card shows the agency name as title and again as its blurb (`presentation.yaml` blurb = name); the dataset header reads "Hospital Services Agency (mock) · Emergency Care · Hospital Services Agency (mock)". The decision text appears twice on the home view (banner and list). The published line prints the full local path of the page.
- **F11. Check names differ by tool for one assertion.** "Expected row count" (Soda, datacontract) vs "Row count" (Evidently).
- **F12. Git setup (environment, not product).** Cloning the worktree gave a repository with missing objects, so `git push` failed with "unpacker error"; worked around with a snapshot commit. Only relevant to reproducing this walkthrough.
