# The actual named tools this pipeline's engines/ stand in for. Verified
# working together in this exact combination - not just requested versions,
# actually pip-installed and run end to end via real_tools/*.py.
#
# Install in TWO steps, not one - a single `pip install -r
# requirements-real.txt` including datacontract-cli's [duckdb] extra
# produces a hard ResolutionImpossible error (confirmed by trying it):
# soda-core-duckdb declares `duckdb<1.1.0`, and pip's resolver won't jointly
# satisfy that alongside the newer duckdb datacontract-cli[duckdb] needs
# (via its ibis-framework dependency) in one transaction, even though both
# tools run fine together at runtime once installed - see below.
#
#   pip install -r requirements-real.txt
#   pip install 'datacontract-cli[duckdb]'   # step 2: needed to run `datacontract test` at all
#
# Step 2 prints a "duckdb 1.x is incompatible" warning and upgrades duckdb
# past soda-core-duckdb's declared ceiling - `pip check` will flag this
# afterward too. Ignore both: dbt-core, dbt-duckdb, soda-core-duckdb,
# datacontract-cli, and evidently were all run end to end (a full
# real_tools/orchestrate_real.py pass, all four tools, all ten runs) against
# whatever duckdb version step 2 lands on (1.5.5 as of this writing, the
# latest release) with no observed breakage - byte-identical results to an
# earlier run made under duckdb 1.0.0, before this was investigated. Don't
# downgrade duckdb preemptively because of the warning; only if you hit an
# actual runtime error.
#
# Wiring up each real tool is described in README.md's "What's real vs.
# equivalent" table and real_tools/*.py's docstrings. Contrary to what this
# file originally claimed before any of these were actually run: the Soda
# checks file and dbt SQL model didn't need to change, but
# contract/bdm-birth-registrations-contract.yaml needed real, structural
# fixes to lint at all under datacontract-cli (wrong shapes for
# description/support/team, an invented rule vocabulary in place of real
# ODCS `metric` names, invalid dimension/enum values), and
# dbt_project/models/staging/schema.yml needed its severity config fixed
# (a "%" suffix on warn_if/error_if isn't real dbt-core syntax) - see each
# file's own comments and README.md's known-disagreements section for the
# full account of what was wrong and how it was found.
