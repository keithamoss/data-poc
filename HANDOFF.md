## What to actually do here

1. **Check your own network access first.** Try
   `pip install -r requirements-real.txt` before anything else. If it
   fails the same way it did in the original session (no PyPI access),
   stop and tell the user plainly — that would mean this environment can't
   do it either, and they'll need a different path (their own machine via
   the device bridge, or checking their org's cloud-environment network
   policy).
2. **Swap SQLite for a real warehouse.** All four engines and
   `pipeline/load.py` use plain `sqlite3` today, which none of the real
   tools (dbt, Soda Core) speak. Point them at DuckDB (simplest — a
   `dbt-duckdb` adapter and `soda-core-duckdb` both exist) or Postgres.
3. **Run the real tools, in place of each engine**, per `README.md`'s
   "Running it for real, later" section:
   - `dbt run && dbt test` against `dbt_project/` (needs a `profiles.yml` —
     not included, since it depends on which warehouse you pick)
   - `soda scan` against `contract/bdm-birth-registrations-soda-checks.yml`
     (needs a `configuration.yml` with real connection details)
   - `datacontract lint` / `datacontract test` against
     `contract/bdm-birth-registrations-contract.yaml`
   - An Evidently `Report` with a `DataDriftPreset` on the `sex` column,
     reference run vs. each subsequent run, replacing `engines/drift_engine.py`'s
     from-scratch PSI computation
4. **Compare real-tool output against the existing equivalents' results**
   (`reports/results.json`, regenerated by `pipeline/orchestrate.py`).
   Where they agree, that's a good sign the equivalents were faithful.
   Where they don't, investigate before assuming either one is wrong.
5. **Update `README.md`'s "What's real vs. equivalent" table** once real
   tools are wired in — move rows from "equivalent" to "real" as they're
   confirmed working, rather than deleting the honest history of what this
   started as.
6. **Keep the Python engines around** as a documented fallback until the
   real tools are confirmed working end-to-end — don't delete
   `engines/*.py` outright in the same pass that wires up the real tools.
7. Commit incrementally with clear messages as each tool comes online,
   rather than one large commit at the end — this makes it easy for the
   user to review progress from their phone as you go.

## Regenerating this repo's current (equivalent-engine) output

```bash
./run_pipeline.sh
```

Regenerates the 10 synthetic runs, loads them, runs all four equivalent
engines, and re-embeds real (equivalent-computed) data into the dashboard
HTML. Useful as a baseline to diff real-tool output against.
